# Work-acceptance record (draft profile 1.4.12, schema 1.2)

A work-acceptance record is a checking party's signed findings about a delivered file, against criteria that were fixed before the check.
It is distinct from a counterparty's acceptance decision (accepted / rejected / disputed). A counterparty acceptance can reference a
work-acceptance record by digest, so "the checker found X" and "the counterparty accepted it" remain two signatures from two parties.

## Properties
1. **Bound to the exact file**: SHA-256 of the delivered file (and of the original, when there is one).
2. **Criteria committed first**: the criteria document has its own SHA-256 and an RFC 3161 timestamp (or a binding to terms the counterparty signed). A verifier
   reports whether the commitment predates the check. The token over `criteria.sha256` is authoritative for when; `criteria.committed_at` is the checker's own claim.
3. **Checker independence is checkable**: `parties.checker` and `parties.producer` are named separately. The checker key must not equal the producer key; a self-check is
   labelled `independence: "self-checked"` and verifiers warn on it. A record that states another value than the parties block supports is reported as inconsistent (step 8).
4. **Verdict vocabulary**: each criterion result is `pass | fail | not-evaluated | error`. The overall verdict is `pass` only if every required criterion is `pass`.
   Any required `fail` makes it `fail`, and `fail` takes precedence over `incomplete`; otherwise any required `not-evaluated` or `error` makes it `incomplete`, never `pass`.
   Verifiers recompute the verdict from the results; a stated verdict that differs is `VERDICT_MISMATCH`.
5. **Verifiable from bytes**: canonical form JCS (RFC 8785). Ed25519 signature over the canonical `receipt` object. An RFC 3161 token over the SHA-256 of the canonical
   receipt. Suites are declared in the record (`canonicalization`, `suite`). No hosted service or account is needed.

## Verification procedure (summary)
1. Parse; refuse an unknown schema, canonicalization or suite.
2. JCS-canonicalize `receipt`; verify the Ed25519 signature with the key named by the signed `receipt.key_id`. The envelope's `signature.key_id` must equal it, else `SIGNATURE_INVALID` (the envelope is unsigned, so it cannot choose the key); whether that key is `parties.checker.key_id` is a separate check (`CHECKER_NOT_SIGNER`). **Key rule:** the public key must be a canonical encoding (y < p) of a point of prime order; any other key (neutral point, small or mixed order, non-canonical) is `KEY_REJECTED` and no signature check is run. That is a finding about the key list, not evidence of tampering. The rule applies to the key named by the signed `receipt.key_id` only; other entries in the key file do not change the outcome fields, and a verifier may report them separately (vector 28). On a signature failure report `SIGNATURE_INVALID`; the remaining checks may still be reported as diagnostics, but the contents are not presented as results. In addition to RFC 8032 verification, which does not require it, the signature's R must be a canonical point of prime order, as the key must be; a verifier must check this explicitly; a signature whose R fails it is not valid (`SIGNATURE_INVALID`; profile 1.4.8, vector 116). Such an R can only be produced with the private key, so this rejects a non-canonical signature from the signer, not a forgery.
3. If the delivered file is supplied, compare its SHA-256 with `files.remediated.sha256`.
4. If the criteria document is supplied, compare its SHA-256 with `criteria.sha256` (`CRITERIA_HASH_MISMATCH`); when it matches, check the results correspond to the criteria (`CRITERIA_RESULTS_MISMATCH`). A criteria document that cannot be read is `CRITERIA_UNREADABLE`: it is not UTF-8, not JSON, uses NaN or Infinity, has a wrongly typed member (such as a criterion id that is not a string), repeats a member name in any object, or holds a lone surrogate (an escape for U+D800-U+DFFF that is not part of a pair). The last two are profile 1.4.8 (vectors 117-118). It is also unreadable when it starts with a byte-order mark (121), holds an integer outside ±(2^53−1) (122), holds a number that overflows to infinity (123), or holds a value, scalar or container, more than 64 levels below the root, the root being level 0 (124-126); these are profile 1.4.11. These four are this profile's I-JSON (RFC 7493) checks, and the list is closed (profile 1.4.12): a noncharacter in a member name or a string value does not make the file unreadable (127, 128). An integer is a number written without fraction or exponent, so `9007199254740992.0`, `9.007199254740992e15` and `1e16` are readable; a number overflows only when it rounds to an infinite double, so underflow (`1e-400`) and digits beyond what a double holds are readable.
5. Criteria commitment. If a timestamp token is supplied, the imprint of its signed TSTInfo (never other bytes of the response, such as `PKIStatusInfo.statusString`; genTime and accuracy come from the same TSTInfo) must be SHA-256 (OID 2.16.840.1.101.3.4.2.1; a same-length imprint under another algorithm is not a match) and equal `criteria.sha256` (`CRITERIA_TIMESTAMP_MISMATCH` otherwise), and its `genTime` is authoritative; a `criteria.committed_at` that disagrees is `CRITERIA_TIME_MISMATCH`. Without a usable token (none, or one over other bytes), fall back to `committed_at` and warn `CRITERIA_COMMITMENT_UNVERIFIED`. The criteria were committed before the check iff the commitment time is strictly earlier than the reference time: the **earlier** of `issued_utc` and the genTime of the record's own token when a token covering the record is supplied, else `issued_utc` (a covering token bounds the check from above; it never moves the signed issue time later). A token's stated `accuracy` widens its time against "committed before"; a token stating none is taken at its genTime; `ordering` is ignored. If not, `criteria_committed_before_check` is `no` and `CRITERIA_COMMITTED_AFTER_CHECK` is raised. **That is a problem, not a warning.**
6. Check the record's timestamp token imprint (SHA-256, as in step 5) against SHA-256 of the canonical receipt; the unsigned `timestamp.digest_sha256` field is informative and never decides the outcome; report `receipt_timestamp` as `none` (no timestamp or no token supplied), `imprint_match` or `imprint_mismatch`. A mismatching token is never used as evidence of time.
7. Recompute the verdict from the per-criterion results (property 4) and compare it with the stated verdict (`VERDICT_MISMATCH`).
8. Emit problem codes (`SIGNATURE_INVALID`, `KEY_REJECTED`, `CHECKER_NOT_SIGNER`, `KEY_COLLISION`, `INDEPENDENCE_INCONSISTENT`, `RESULT_VOCABULARY`, `VERDICT_MISMATCH`, `CRITERIA_HASH_MISMATCH`, `CRITERIA_RESULTS_MISMATCH`, `CRITERIA_UNREADABLE`, `CRITERIA_TIMESTAMP_MISMATCH`, `CRITERIA_TIME_MISMATCH`, `CRITERIA_COMMITTED_AFTER_CHECK`, `RECEIPT_TIME_UNREADABLE`) and warning codes (`SELF_CHECKED`, `PRODUCER_UNDECLARED`, `CRITERIA_COMMITMENT_UNVERIFIED`). The record is accepted as stated when the signature is valid and there are no problem codes. Code lists are sets: compare without regard to order. `PRODUCER_UNDECLARED` follows the parties block (no producer named), whatever the record states; a stated `independence` that differs from the derived one is also `INDEPENDENCE_INCONSISTENT`. **Derived independence:** names are compared after removing leading and trailing white space and Unicode lower-casing; a name that is null, `false`, a number equal to zero, or an empty string, array or object counts as absent, and any other value that is not a string counts as declared. Derived independence is `undeclared` when there is no `parties.producer` or its `name` is absent, null, empty, `unspecified` or `unknown` (20, 109); otherwise `self-checked` when the producer and checker names are equal, when the two keys are one key, or under the key rules of steps 10 and 11 (a key entry that cannot be read, 69; and, only when the record claims `independent`, a stated `key_id` that is empty or not listed once, 80, 81, 103); otherwise `independent`. **Stated and derived:** the outcome member `independence` reports the record's stated value, and `SELF_CHECKED` is warned when the stated value is `self-checked`; a derived value that differs is reported as `INDEPENDENCE_INCONSISTENT` (13, 108). A record that states `self-checked` while naming different parties is therefore inconsistent unless the two keys are one key or a key entry cannot be read (108). A record refused at step 1 has the outcome `{"refused": true, "reason": "unknown schema, canonicalization or suite"}`.
9. Time-stamp authority. The outcome fields cover imprint and time only. A verifier that presents a time as evidence to a third party should also validate the token's CMS signature and certificate chain against authorities the relying party trusts, and report that separately. **Profile 1.4:** the outcome may carry `tsa_signature`, an object with keys `criteria` and/or `receipt` (one per token present). Without relying-party anchors (none supplied, or an empty list) it is `not_evaluated`, and an absent field reads the same. With anchors it is `verified` (CMS signature, the `contentType` signed attribute equal to an `eContentType` of `id-ct-TSTInfo` (RFC 5652 §5.3), ESS signing-certificate binding, `id-kp-timeStamping`, and a chain of CA issuers reaching a supplied anchor (matched by subject name and public key, RFC 5280 §6.1.1, not by certificate bytes; an anchor with the issuer's name but another key is not that issuer, so if only such anchors fail the value is `untrusted`), with the signer and every issuer other than the anchor valid at genTime; a root inside the token is not an anchor), `failed`, `untrusted`, `unsupported` (e.g. a curve other than P-256/P-384; RSA PKCS#1 v1.5 and ECDSA P-256/P-384 are required, RSASSA-PSS is optional) or `no_signer`. It never changes any other outcome member. When a token has more than one defect, the value is `failed` if any check that can run fails; otherwise `no_signer`, then `unsupported`, then `untrusted`. An issuer in the token that fails a check is `failed` whether or not the chain reaches a supplied anchor.
10. **Profile 1.4.2 rules** (vectors 60-90; vectors 01-57 and their outcomes are unchanged).
    - *Canonical base64.* Every base64 value read is canonical: the standard alphabet, `=` padding to a multiple of four, no whitespace, and re-encoding the decoded bytes gives the input string. A non-canonical signature value is `SIGNATURE_INVALID`; a non-canonical public key is `KEY_REJECTED`; a token or criteria file that is not canonical base64 matches nothing: it is reported as the corresponding mismatch (`CRITERIA_HASH_MISMATCH`, `CRITERIA_TIMESTAMP_MISMATCH`, or `imprint_mismatch` for the record's token), never as a refusal (60-63, 89, 90).
    - *Lowercase digests.* A SHA-256 digest in a record is exactly 64 lowercase hex digits; upper case matches no digest (67).
    - *Repeated key identifier.* A `key_id` listed more than once in the key list is `KEY_REJECTED`, whichever entry comes first. If it is the signing key's, no signature check is run; if it is the producer's or checker's, independence is derived as `self-checked` (75, 79).
    - *Form of `genTime`.* DER GeneralizedTime in UTC: `YYYYMMDDHHMMSS`, optionally `.` and digits whose last is not `0`, then `Z`; real calendar fields. Any other form is no usable time and the token is treated as giving none: warning `CRITERIA_COMMITMENT_UNVERIFIED` and fallback to `committed_at` (70-74, 78). A fraction is kept to the millisecond; the criteria time is rounded up and the reference time down, and "before" is strict `<` (66, 68).
    - *Stated times.* `committed_at` and `issued_utc` are RFC 3339 UTC, `YYYY-MM-DDTHH:MM:SS[.fff]Z`. A stated time that step 5 uses and that is in another form gives `RECEIPT_TIME_UNREADABLE` and `criteria_committed_before_check: no`, not `CRITERIA_COMMITTED_AFTER_CHECK` (76). Step 5 always uses `issued_utc`; it uses `committed_at` only when no usable criteria token supplies the time. When one does, a `committed_at` in another form is `CRITERIA_TIME_MISMATCH` (88).
    - *Independence by key.* Keys are compared as decoded bytes: two identifiers whose entries decode to one public key are one key (`KEY_COLLISION`, `self-checked`; 65, 87). A key entry for a stated producer or checker identifier that is not canonical base64 is `KEY_REJECTED` and independence is `self-checked` (69). When a party's `key_id` is stated and `independence: independent` is claimed, that `key_id` must be non-empty and listed once, else `INDEPENDENCE_INCONSISTENT` (80, 81); a producer with no `key_id` rests on the party names (82).
    - *Checker is the signer.* `CHECKER_NOT_SIGNER` compares the checker's `key_id` with the one the signature was checked under (the signed `key_id`), never the unsigned envelope's. An envelope naming another key is `SIGNATURE_INVALID` only (64, 86).
    - *Unsigned attributes.* Unsigned attributes of a token's SignerInfo are not read and are no ground for refusal (83).
    - *Types.* A record or input whose objects, arrays or strings have other types than the specification gives is refused as an unsupported schema, and never makes a verifier fail (77).
11. **Profile 1.4.3 clarifications** (vectors 91-107; no outcome of vectors 01-90 changes).
    - *Keys.* The canonical-key rule applies to the keys a verification uses: the signer's entry and any entry a stated party names (69). An entry that no party names and that did not sign is not read, so a non-canonical key there is not `KEY_REJECTED` (91). A key identifier listed more than once among entries that are not read is still `KEY_REJECTED` (79). An empty signed `key_id`, or an empty envelope `signature.key_id`, names no key: `SIGNATURE_INVALID`, not a refusal (104).
    - *Record token.* A record token that is not canonical base64 gives `tsa_signature` `not_evaluated` without anchors and `failed` with anchors (93, 92).
    - *Digests.* A digest member of the wrong length or with other characters is not refused; it matches nothing, so the matching check reports its mismatch code (94). In the outcome the digest member that is matched is `criteria.sha256`: `CRITERIA_HASH_MISMATCH` when the criteria document is supplied, `CRITERIA_TIMESTAMP_MISMATCH` when a criteria token is supplied. `files.remediated.sha256` is compared only with a delivered file in hand (step 3), which a vector does not carry; `timestamp.digest_sha256` is unsigned and not used (101); other digest members are not matched.
    - *Times.* A fraction in `committed_at` or `issued_utc` has one to three digits (`.5` is readable, 95; four digits is `RECEIPT_TIME_UNREADABLE`, 96; in `committed_at`, where step 5 uses that time, the same with warning `CRITERIA_COMMITMENT_UNVERIFIED`, and when a usable criteria token supplies the time it is `CRITERIA_TIME_MISMATCH` instead, as in 88). Second 60 is not a calendar value (97). `genTime` is rounded to the millisecond first (commitment time up, reference time down), then the accuracy is applied (98); `CRITERIA_TIME_MISMATCH` is raised unless `committed_at` equals the `genTime` date and time to the second, written without a fraction; a `genTime` fraction is dropped for this comparison (99), so a `committed_at` with a fraction always raises it; rounding and accuracy (98) apply only to the "committed before" comparison.
    - *Form of `genTime`.* The fraction is `.` followed by one or more ASCII digits (last digit not `0`, as in 1.4.2), and every numeric field is its exact number of ASCII digits. A fraction with a sign, separator or blank, or an empty fraction, is not read as a time (105). The authority check reads `genTime` by the same form rule as step 5; a `genTime` that is not usable for step 5 makes `tsa_signature` `failed` when anchors are supplied (105, 107), because validity at `genTime` cannot be established; its imprint still sets `receipt_timestamp` (78). When the check goes on, it takes the time as read (a fraction as written, not rounded) as the time at which the signer and issuer certificates must be valid.
    - *Checker.* Another identifier listed for the signer's own key names the signer: `CHECKER_NOT_SIGNER` (100). A stated checker identifier that is empty or not listed gives `self-checked`, `CHECKER_NOT_SIGNER` and, when the record claims independent, `INDEPENDENCE_INCONSISTENT` (103); for a stated producer identifier that is empty or not listed only `INDEPENDENCE_INCONSISTENT` results (80, 81). If the signed `key_id` and the checker's are both empty they are equal, so there is no `CHECKER_NOT_SIGNER`: `SIGNATURE_INVALID` and, when the record claims independent, `INDEPENDENCE_INCONSISTENT` (106, the exception to the rule above; derived independence is still `self-checked`, and no key is named).
    - *Types.* A wrong-typed `timestamp.digest_sha256` in the unsigned envelope, or `receipt.payment` and its members, is noted, not refused: no problem or warning code is reported and the outcome has no member for the note (101, 102). These two members are an exception to the wrong-type refusal rule (77).

12. **Profile 1.4.5: the relying party's keys** (vectors 110-111; the point rule for the producer's key, profile 1.4.7, vectors 114-115; no outcome of vectors 01-109 changes). `keys` is the key file the issuer serves. A relying party may also supply `relying_party_keys`, a key list it obtained itself, outside the issuer's response (for example from the producer's own key document). When it is supplied, the record claims `independent` and the producer states a `key_id`, the producer's key counts only when `relying_party_keys` holds the same decoded key; otherwise derived independence is `self-checked` and the record is `INDEPENDENCE_INCONSISTENT` (110, 111). Entries compare as decoded bytes under step 10's canonical-base64 rule; an entry that does not decode matches nothing (112). Entries are matched by key, not by `key_id`, so a repeated `key_id` changes nothing and the repeated-identifier rule (75, 79) does not apply to them (113). The producer's key must pass step 2's point rule (a canonical point of prime order): a small-order key such as the neutral point is held by no one and identifies no producer, so it never establishes the producer's key and derived independence is `self-checked` (114, 115). A producer key found only in the issuer's response, listed or used to sign, does not establish the producer's key. Without `relying_party_keys` the rule is not applied, and `keys` is read as the relying party's list, as before (119). The point rule for the producer's key applies only under the conditions above; under a `self-checked` claim it is not applied, and derived independence decides as for any record (120). Where the key came from shows who controls it, not that its holder is a party other than the issuer.

never trust them. The timestamp tokens in the vectors are imprint-and-time fixtures, not valid RFC 3161 tokens: their SignedData has no SignerInfo, so OpenSSL and other CMS parsers that require a signer refuse them. They test imprint and time handling only. Vectors 31-36 instead carry real RFC 3161 tokens (FreeTSA and DigiCert, fetched 2026-10-20), and 37-46 (except 43) tokens from a test-only PKI (openssl 3.5, re-signed at a fixed genTime; the test root is not a real authority), and relying-party anchors in `inputs.tsa_roots_base64`.

## Reference verifier (`verifier/`)

`verifier/war_verify.py` runs the procedure above using only the Python standard library (Ed25519, JCS with RFC 8785 numbers, reading the token's signed TSTInfo, and the profile 1.4 authority-signature checks are implemented in the file), with no network access:

    python -I verifier/war_verify.py vectors/*.json

`verifier/check_payment.py` (standard library, network) checks a receipt's optional `payment` member against the chain:
EIP-3009 `authorizationState(payer, nonce)` on `asset`, and, given `settlement_tx`, the `AuthorizationUsed` and
`Transfer(payer, pay_to, amount)` logs and a block no later than `issued_utc`. It reports `verified`,
`authorization_used`, `not_found`, `mismatch` or `unsupported` (also for a member outside the form: all members strings,
`network` `eip155:` plus a decimal chain id, `amount` a decimal string, 0x-hex addresses and nonce, no other members),
and changes no outcome:

    python -I verifier/check_payment.py receipt.json

It prints `AGREE` or `DIFF` per vector and exits non-zero on any disagreement; `--outcome FILE` prints the computed outcome object. It checks token imprints, times and accuracy; the authority signature (step 9) is evaluated when anchors are supplied, from a vector's `inputs.tsa_roots_base64` or `--tsa-roots FILE`. It is offered as a reference for comparison; clean-room verifiers that disagree with it, or with a vector's `expected` object, are the useful result.

The file `verifier/war_verify.py` implements profile 1.4.12 and agrees with all 128 vectors. With `WAR_VERIFY_STRICT=1` an internal error is raised instead of being reported as a refusal.

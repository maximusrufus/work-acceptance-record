# Spec ambiguities and the reading chosen (written before freeze)

1. Preflight vs malformed pass for EIP-712 body defects. AR-35 step 2 says preflight fails when the typed message cannot be built (AR-6/10/11). I treat "cannot be built" as: wrong type/form of any member the 12-field message uses (version, issuedAt, 3 hex32, signer AR-11, strings, authority/subject sub-members). Extra body/authority/subject members, empty `deliveryIssuer`, and disposition value (AR-1) are NOT preflight: they go to the malformed pass (after the signature). Same outcome unless a key_unresolved/signature_invalid would pre-empt.
2. JWS payload parse at preflight covers I-JSON/number lexical form and "object with non-empty string signer" only; member forms (AR-5), shape (AR-4), AR-1 and JCS equality (AR-16) are the malformed pass.
3. Order inside the EIP-712 contract-account branch. AR-12 classification, then `contractAccounts:false` -> `contract_accounts_unsupported`, then the AR-14 signature-format check (`signature_invalid`, no call), then call lookup (`chain_state_unavailable` if unlisted). Spec does not say whether unsupported precedes the format refusal; I put unsupported first (key step runs before signature checks).
4. Account not listed in `chain` for (signerChainId, account): `key_unresolved/chain_state_unavailable` for both ordinary and contract accounts (AR-12). A `chain` entry matches on chainId and lowercase account; `block` ignored.
5. `policy_refusal` for JWS `key_missing`, `signer_mismatch`: `trust.complete is True`. `key_refused`: AR-36 text says "not resolved from trust.keys (AR-18, AR-19) and complete is a declaration" so key_refused would also be true when complete is true; I follow that literally (CASES C20 uses the string "true", so not exercised). EIP-712 key_unresolved: false.
6. AR-27 "verification rule 1" includes "payer and payee are distinct non-null entities"; I apply it (case-insensitive for 0x+40hex addresses, byte-exact otherwise) and a failure makes the subject unavailable. I do not apply rules 2-4 (spec says so).
7. Subject `signer.signature` is `base64url:` + unpadded base64url of 64 bytes (per the extension example). Missing prefix -> unavailable. Subject `payment.network`, `amount`, `asset`, `payee` are not required for the subject to be available; they only matter for offer matching (no match -> evidence_unavailable). Payer is absent (not unavailable) if network is not `eip155:<decimal>` or payer is not 0x+40 hex.
8. Ed25519 equation: cofactorless `[S]B = R + [k]A` after requiring A and R canonical of order exactly L and S < L (AR-19/20). With both of order L the cofactored and cofactorless equations coincide.
9. Issuer key lists: Ed25519 `kid` in `trust.issuers` is ignored; a JWS offer verifies if any listed Ed25519 key for the issuer verifies it (kid in header not compared). EIP-712 offers: recovery tolerates v in {0,1,27,28} and high-s (the extension demands neither strictness); recovered address compared case-insensitively to listed addresses.
10. Offer `validUntil`: if present and non-zero must be >= outcome time. A literal 0 in JWS form is "not non-zero" and imposes no condition (the spec only says EIP-712 0 means absence; reading the condition as applying to non-zero values only gives the same effect). Offer `version` must be integer 1.
11. AR-33 "the key that verified the record is listed": EIP-712 -> signer account in the issuer's `address` list; JWS -> trust.keys key bytes in the issuer's `ed25519` list. "or signed the subject record": JWS key equals the authenticated subject's `signer.publicKey`. Only the entry with `issuer == deliveryIssuer` is consulted.
12. AR-25 `outcome` bytes comparison runs only when the subject is available (AR-35 step 4 gates AR-24..26 on subject availability).
13. AR-24 ties `contextId` to the subject's computed identity and `subject.reference` to it; both compared; a single condition is reported if either differs.
14. AR-16 byte comparison for JWS uses own JCS over the parsed body; ints above 2^53 make JCS unsupported -> member_invalid (already invalid under AR-5).
15. Duplicate `kid` in `trust.keys` raises InputRefused (no result), per AR-18. Matching ignores `key` validity of other entries.
16. Envelope `signature` for EIP-712 that is not a JSON string is `acceptance_member_invalid` (AR-7 shape); a string of the wrong form is `signature_invalid` (AR-13/14).
17. Empty-string `confirmingParty` with a JWS-form `trust.keys` match still proceeds to signature check (AR-34 is in the malformed pass).
18. Terms artifacts that are not valid JSON/profile are silently disregarded (AR-29 "disregarded"); `trust.authority` entries must match the four members exactly.
19. EIP-7702 delegation designators: no special handling (code true -> contract path, AR-12).
